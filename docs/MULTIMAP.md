# 第一阶段多地图测试

本轮测试使用项目内实际的 C++ `BotRuntime`，覆盖 JSON 感知解析、地图记忆、BFS、第一阶段决策、动作编码和回执处理。测试配置和全图只由测试驱动持有，机器人只接收当前视野。

## 怎样复现

生成固定地图集（15 张专项图 + 40 张随机图，随机种子从 20261022 开始）：

```bash
python3 scripts/generate_multimap.py
./scripts/test_offline.sh
mkdir -p build/multimap
./build/offline/rmtc_multimap \
  rmtc_ws/src/rmtc_bot/test/maps/stage1_suite.json build/multimap/final.json
```

每图运行 100 Tick。C++ 测试环境按阶段一规则处理单车四向移动、障碍、收集及回执，实际裁判程序未参与这一层测试。随机图包含 12×12、20×20、24×24 和 28×12 四种尺寸、5%～35% 障碍密度及不同出生位置。

每张图都检查：动作齐全、Tick/场次正确、动作类型合法、回执可读、终局不再发布动作、达到该场景采集下限。随机图采集下限为 `min(100, 出生点连通区域的资源价值)`，这是本地图集的回归标准，不是赛事规则。专项图单独规定采集下限，包括被墙隔开的资源和超出 100 Tick 的目标。

测试端另算“从出生点出发、单独前往时 100 Tick 内可达的资源价值之和”，仅作为上界参考。它没有计算收集全部资源的最优旅行路线，因此不能直接用于声称策略达到最优。

真实 ROS 和随包裁判的批量测试：

```bash
./scripts/build.sh
source /opt/ros/humble/setup.bash
python3 scripts/test_multimap_referee.py \
  --practice-dir /你的路径/rmtc_practice \
  --report-dir build/multimap-referee-final
python3 scripts/report_multimap.py
```

默认选择九张图，按 100 ms/Tick、100 Tick 测试，包含两张固定随机图。驱动启动独立裁判，默认仅本机、ROS 域 195、网页端口 18089；需使用空闲域和端口，工具不连接已有网页服务。一个机器人进程连续接收不同场次，验证地图尺寸和场次切换。练习端配置由驱动通过本地管理接口部署，不传给机器人。

驱动检查所有 100 个动作 Tick、100 个回执 Tick、最终动作 Tick 99、最终裁判结算中 Tick 99 来源为 submitted、非法动作数、采集下限；每图保存结果，并在退出时关闭自己启动的进程。完整日志和逐 Tick 轨迹在 `build/` 下，精简结果保存到 [multimap-results.json](multimap-results.json)。

`callback_us` 包含本地感知序列化/解析至动作生成，ROS 记录为节点回调耗时；两者测量边界不同。该数据不包含整条 DDS 传输延迟，也不是优化前后性能对照。

## 本轮发现

1. 视野半径为 0 时，旧版只把已知空地边缘当探索目标；目标刚好是自身位置，策略最终一直等待。现在该情况下提供相邻未知格作为探索目标。开放地图专项图从 0/20 改为 20/20，其余 54 张图采集值保持一致。未将未知格误标为已知空地；盲探遇障碍仍按回执处理，零视野复杂障碍地图的持续避让尚未覆盖。
2. 随机图 `random_31` 的出生连通区域与所有资源隔绝，采集 0 的原因是地图不可达。该图仍用于验证程序安全等待、不撞墙及不提交非法动作。
3. 首轮六张裁判图中，`sealed_high_resource` 的监测日志少 Tick 74 动作，`long_corridor` 少 Tick 86 动作；资源结果达到预期，回执齐全。初始日志不能确定这是监测遗漏还是未发布，因此该轮按失败保留在 `build/multimap-referee/report.json`。随后增加节点发布动作日志、将调试日志限制到机器人节点，并复测；复测九图均记录齐全。复测结果单独记录，不覆盖初轮。

离线 40 张随机图平均采集 171.25/200，13 张收齐 200。地图并非正式赛图；资源分布、可达性和 100 Tick 路线限制均会影响结果，此均值不代表正式成绩。

4. 九图复测中长走廊的网页 `executed_tick` 一度为 98，但节点日志确认已发布 0～99 的全部动作。最终裁判 `score.json` 明确 Tick 99 动作来源为 `submitted`、状态 `wait`，确认是诊断字段异步更新造成的误报。测试工具加入结算等待，并使用最终裁判动作来源核验；只读取该文件的结算动作片段用于测试报告，不提供给机器人。原始复测报告保留在 `build/multimap-referee-final/report.json`，附结算核对的报告为同目录 `report-audited.json`。

## 结果

- 55 张离线地图全部达到各自断言，0 非法动作、0 撞障碍/越界尝试、0 漏动作、0 回执错误。原有 113 个回归场景也通过。
- 九张真实裁判地图结算核对通过，九图共 900 个动作 Tick 和 900 个回执 Tick 齐全，0 非法动作。闭环测试和裁判测试是两套独立运行结果。
- 40 张固定随机图平均采集 171.25/200、13 张收齐；唯一零采集随机图没有与出生区域连通的资源。
- 视野为 0 的开放图采集值由 0 修复为 20，另八张真实裁判图与本地对应采集值一致。
- 性能数据、地图集及源码 SHA-256、每图结果见 [精简结果](multimap-results.json)。完整逐 Tick 轨迹 `build/multimap/final.json` 约束于本次本机测试，不作为正式成绩。

长走廊使用修正后的测试驱动单独再跑一场：采集 20/20，100 个动作及回执齐全，0 非法动作，结算核验通过。记录位于 `build/multimap-referee-corridor-check/report.json`。
