# 第一阶段连续采集规划对比

本次在 `Stage1Policy` 加入有界的连续采集规划，仅依据当前及历史合法视野中的资源，不读取测试全图。

有至少两个可达资源时，用现有 BFS 获取资源间距离，搜索最多六次采集的短路线；每层保留最多 64 条候选，最多考虑 16 个资源。收益按到达时间衰减，兼顾近期收益与后续采集。每个新 Tick 根据实际位置和视野重算。没有足够资源目标时沿用原决策引擎的采集/探索行为；死亡、终局、剩余 Tick 限制仍生效。同 Tick 重发复用完整的采集决定。

搜索会增加计算量；这次目标是改善采集量，并非降低寻路耗时。尝试过按新发现区域大小选择探索目标，但结果有得有失，最终未采用该改动。

## 对比结果

所有数值均为 100 Tick 采到的资源价值，满资源图总价值 200；不是正式比赛分数。

| 地图组 | 数量 | 旧版平均 | 新版平均 | 提升 / 下降 / 持平 |
| --- | ---: | ---: | ---: | --- |
| 原有随机图，参与选择方案 | 40 | 171.25 | 173.50 | 6 / 3 / 31 |
| 新增开发图，参与选择方案 | 80 | 158.125 | 158.000 | 6 / 5 / 69 |
| 独立保留图，确定方案后测试 | 200 | 168.85 | 169.65 | 27 / 14 / 159 |

保留图平均提升 0.8 资源价值，幅度较小，不能据此保证正式赛图一定涨分，也没有证明统计显著性。当前选择保留该方案，同时公开退步图；后续仍有策略调优空间。

开发组 `random_31` 旧、新均采到 80，低于该测试图的 100 点下限；保留组 `random_126` 旧、新均采到 90，也低于 100 点下限。没有降低断言来制造“全部通过”。这些图未达采集目标，且两组没有发现动作类型、Tick/场次、漏动作、回执处理错误。

旧、新版本在每组使用相同地图、相同 Tick 预算和相同感知范围。旧版测试二进制在修改策略前保存，双方共享已完成的底层修复。原有固定图及这轮专项图保持一致；没有使用测试全图指导机器人。

原有 55 图回归及核心测试仍需通过，不能用均值提升抵消功能性失败。新增了直接调用策略时同 Tick 缓存完整结果和终局剩余 Tick 的回归。

## 复现及记录

```bash
./scripts/test_offline.sh
python3 scripts/generate_multimap.py --seed-base 20261101 --random-count 80 \
  --output build/collection-upgrade/validation.json
python3 scripts/generate_multimap.py --seed-base 20261201 --random-count 200 \
  --output build/collection-upgrade/holdout.json
./build/offline/rmtc_multimap build/collection-upgrade/holdout.json \
  build/collection-upgrade/holdout-after.json
```

新增两组按固定种子生成，不能把目录中的全图文件传给机器人。`rmtc_multimap` 是持有全图的本地测试环境，内部只向 `BotRuntime` 发送当前视野。

逐 Tick 记录和修改前保存的基线程序在 `build/collection-upgrade` 下；它们属于本次本机测试产物，不进入比赛程序。生成开发/保留图的默认采集下限可能使测试程序返回 1，应检查具体失败条目，不忽略退出码。

机器可读的分图成绩、完整退步列表、源码校验值和裁判复核结果见 [collection-comparison.json](collection-comparison.json)，可用 `python3 scripts/report_collection_comparison.py` 从本次产物重新汇总。该命令需要前后版本的结果文件，不能替代重新运行基线。

旧的 [多地图报告](MULTIMAP.md) 和 `multimap-results.json` 保留为改进前的历史记录，不覆盖。当前策略源码的行为与该历史报告不同，以本对比报告为准。
