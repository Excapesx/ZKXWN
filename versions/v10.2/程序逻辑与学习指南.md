# 10.2程序怎么工作

每一帧先接收本队公开感知。parse.cpp把JSON变成本队位置、血量、资源价值、有效伤害、已完成任务ID和可见实体；FrameGate检查场次与Tick，新场清空旧记忆。WorldMap只保存合法看到的信息。

score_model.hpp回答“如果做成这件事，按规则能多几分”。资源120封顶30分，伤害500封顶15分，合格任务每ID5分。它计算预测结果与当前状态的差；资源价值20与80时，同枚普通资源都加2.5分。部分任务进度和死亡缓冲的辅助值单独保存，不能当作实际得分。

opportunity_evaluator.hpp回答“公开信息里哪些路线可能做成”。它比较资源和坐标任务的短组合，使用累计到达时间、可见对手ETA和信息新鲜度；候选数、路线深度和展开数有上限。每Tick只执行第一步，下帧根据真实回执和新视野重新判断。

bot.cpp先处理死亡、保护、强制等待和危险事件，再比较攻击、资源、任务、事件、观察和追猎。短资源路线后仍能完成的坐标任务，不应把其全部5分看成“立刻过去才有的独占收益”；本版将可恢复后续价值作为明确的辅助扣减。分时偏好仍保留，因为开发对照中的取消分时版本更差。

选出动作后做合法性校验，再发布本队action话题。node.cpp的score_audit记录规则收益、辅助值、ETA、风险和原因；动作是否执行仍要看下一帧回执。receipt_audit.hpp和scripts/audit_bag.py用于核验，不会自动重发旧Tick，也不读取隐藏状态。

LLM异步处理本场公开自然语言公告，经校验形成Plan。正式任务资格由官方判定，本地mock或成功解析不能代替。10.2的任务收益日志始终注明资格成立时的条件估计。

建议阅读顺序：types.hpp → score_model.hpp → opportunity_evaluator.hpp → bot.cpp的stage2 → node.cpp的score_audit → phase_policy.hpp与receipt_audit.hpp。先复述“当前还能加什么分、眼前有什么机会、为什么值得这一步”。

CMakeLists.txt负责哪些.cpp编进库、哪些程序链接这个库及需要哪些依赖；它不负责攻击或采集决策。改策略去src/rmtc9，增加新的.cpp才需要同时维护构建目标清单。新增的评分和机会模块是头文件，通过现有bot.cpp参与编译。

当前候选的模拟没有证明提升，同场存在退步；不要把源码更复杂或日志更多当作已经更强。先从验证报告中的一帧和一个小例子学习，再进行官方练习的实机核验。
