# 校内8.0 性能验证报告

## 结论

在离线仿真里，同一张地图、同一席位、同一批对手的条件下，8.0 在全部 28 组场景中都不低于 7.0。

- 第一阶段（独立采集，标准 20×20、视野 4）稳定高 0.6–0.7 分。
- 第二阶段：对手越弱，差距越大。3×7.0 阵容 +0.73；贪心、只采集、掉线这类对手 +2.3 到 +3.0；1 对 1 +4.85。
- 事件局 +0.5 到 +0.9；模型输出不规整时差距还会扩大。

对手全是 8.0 时只有 +0.31（区间含 0）；让 8.0 和 7.0 坐进同一局直接比时基本打平（+0.06）。8.0 的提升来自“自己拿分更稳”，不来自针对 7.0。

## 方法

- **测评工具**：`tools/bench/`。离线裁判按规则 PDF §5.2 的同 Tick 顺序结算：
  1. 事件激活
  2. 事件死亡
  3. 固化动作
  4. 战斗（击杀奖励、反伤、易伤、无双）
  5. 移动（幻术、临时墙）
  6. 入点事件（天使、辣椒）
  7. 堡垒驻留与回血
  8. 死亡扣除
  9. 资源、任务、复活与保护

  计分：资源 30×min(R/120,1) + 对抗 15×min(D/500,1) + 任务 5×M。D 含击杀奖励和死亡扣除。
- **对手**：冻结的 7.0（`baseline_v7/`，与校内7.0 逐字相同，经适配器只传公开感知字段），以及四种代表性程序：
  - 贪心：相邻才打，否则去最近资源
  - 冲锋：看见就追着打，射程 1–2
  - 只采集：从不攻击
  - 掉线：一直等待
- **seat 模式（默认）**：每张图、每个席位，先放 8.0 打一局，再放 7.0 打一局，其余三个席位的程序和顺序完全相同。比较这个席位上两者各自的得分。
- **事件**：两套参数，standard 是规则正文的标准数值，practice 是官方练习包 `stage2.json` 的数值。每张图随机生成 8 种事件各一次，公告后 2 Tick 由“理想模型”把公告翻成结构化 JSON，交给双方各自的 `parse_plan`。`--noise` 模拟模型输出的常见毛病：1 = 同时写 events 和 hazards，2 = 夹一条认不出的条目，3 = Markdown 包裹加说明文字。
- **地图**：随机图生成器与 7.0 相同（四角出生、13% 障碍、16 个资源）。另外直接读取官方练习包的 `stage1.json`、`stage2.json`。
- **样本外**：调参只用了种子 83000 起（第二阶段）和 50000 起（第一阶段）。下表全部来自从未参与调参的种子。
- **统计**：95% 区间按地图整组自助抽样 2000 次，不把同图的 4 个席位当成独立样本。
- **完整性**：`evidence/validation/frozen_sources.json` 记录了 `src/`、`baseline_v7/src/`、`tools/bench/` 每个文件的 SHA256，测评结束时复核未变。8.0 对 8.0 的对称检查分差严格为 0，说明测评工具本身不偏向任何一方。

## 真实节点端到端（`evidence/node_sim/`）

用 `tools/node_sim/` 的 ROS 替身头文件编译真实的 `node.cpp`、`llm.cpp`、`curl_transport.cpp`：
- 离线裁判按协议格式生成感知 JSON（9×9 相对位置字符串、event_text、score 等）喂给节点。
- 节点发布的动作 JSON 逐条校验 tick、session_id 和字段。
- 模型请求通过 libcurl 发往本地假网关 `mock_gateway.py`。

每 Tick 100 ms，标准事件，每种设置跑 2 场，其余三席为 7.0：

| 设置 | 节点 | 网关请求 / 成功（2xx） | 用上的事件计划 | 动作缺失 / 回填错误 / 格式错误 / 无效动作 |
| --- | --- | ---: | ---: | --- |
| 模型每次 0.15 s | 8.0 | 45 / 45 | 45 | 0 / 0 / 0 / 0 |
| 模型每次 0.15 s | 7.0 | 45 / 45 | 44 | 0 / 0 / 0 / 0 |
| 模型每次 3 s（慢模型） | 8.0 | 26 / 26 | **26** | 0 / 0 / 0 / 0 |
| 模型每次 3 s（慢模型） | 7.0 | 35 / 35 | **0** | 0 / 0 / 0 / 0 |
| 网关每 3 次请求返回一次 502 | 8.0 | 67 / 45 | 45 | 0 / 0 / 0 / 0 |
| 网关每 3 次请求返回一次 502 | 7.0 | 67 / 45 | 43 | 0 / 0 / 0 / 0 |

两个节点每 Tick 都发出了合法动作，第 0 Tick 都取得了资格调用（这是 7.0 已有的正确行为）。差别在慢模型：7.0 的客户端 2.5 s 就放弃，网关那边已经成功并计了 35 次配额，节点却一份计划都没用上，而且不会报任何错误。8.0 等到结果并全部采用，请求次数还更少（节流）。原始输出在 `evidence/node_sim/*.out`。

## 决策耗时

离线测量，10 线程并发，含线程争用，所以偏保守：
- 无事件：8.0 p99 约 0.16 ms，最大 5–30 ms，偶发于开局路线的精确 DP 与多次 BFS 同时发生时。
- 有事件：时间展开 BFS 较重，p99 约 3.3 ms，最大约 60 ms；7.0 在同样条件下最大约 56 ms。
- 第一阶段：p99 约 0.4–0.6 ms，最大约 8 ms。

都远小于第一阶段 100 ms、第二阶段 500 ms 的动作窗口，但不包含 DDS、模型和 ROS 发布链路。

## 不能据此得出的结论

1. 离线仿真不是官方裁判。地图生成器、对手程序和事件安排都是本包自己写的；正式比赛的地图、事件和对手都不同。
2. “理想模型”给出的是完全正确的结构化事件，真实模型会出错。噪声实验只覆盖了三种常见毛病。
3. 四人局里 8.0 对强对手（3×8.0）的优势不显著；资源总量固定是结构性上限，靠调参无法再翻倍。
4. 任务分的 AI 资格在离线测评里假设已具备；真实资格只能由本场真实成功调用取得。
5. ROS 替身只验证了节点逻辑和协议格式，不能代替 Ubuntu + ROS 2 Humble 的构建、DDS 发现和现场检录。
