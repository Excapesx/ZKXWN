# 10.1程序怎么工作

每一帧先收到裁判公开感知，解析本队位置、血量、资源、伤害、任务、可见敌人与事件。FrameGate检查场次和tick；新场清空旧记忆。Bot把本队看到过的内容写入WorldMap，用BFS得到合法目标距离。

第一阶段寻找预算内能收走的资源路线，并在条件合适时把观察点纳入；尾盘重新核算预算。第二阶段先处理强制等待、事件和生存，再生成攻击、资源、任务、事件、探索与追击候选。resource_race.hpp给资源补上双方到达时间的估计；候选路线的第2、3站会使用累计到达时刻。预测不等于敌人下一步实际选择，因此只在条件明显更优时替换原路线。

选出动作后先做合法性检查，再发布/team_A/action之类的本队话题。receipt_audit.hpp记录上一条动作期待的tick与种类；下一帧回执不同或感知跳tick时写日志，保留原因未知。日志不会自动重发旧tick指令，也不读取隐藏赛场状态。scripts/audit_bag.py在赛后检查录制。

LLM独立异步处理本场公告，经校验后形成Plan，Bot用Plan构建危险场和有益事件目标。正式LLM资格由裁判判定，离线mock不替代资格。

CMakeLists.txt列出哪些.cpp编成核心、哪些测试和工具链接核心；攻击或资源决策写在src/rmtc9对应文件。CMake负责构建关系和依赖，不负责替你决策。ROS包CMake需要保持与根核心源文件清单一致。

阅读顺序：types.hpp → bot.hpp → bot.cpp的decide → stage1/stage2 → resource_race.hpp → receipt_audit.hpp → ROS node.cpp。先用自己的话描述一帧数据怎么变成一条动作，再逐个看分支。

本版从phase_policy.hpp开始看分时逻辑：tick表示现在到第几回合，maxTicks表示本场共几回合；两个数决定当前时段。bot.cpp再检查附近资源、血量和敌人，决定是否真用采集加成。可以复述为：“时间告诉程序现在偏向做什么，感知告诉程序现在有没有机会这么做。”
