## 在克隆的仓库中运行

需要Ubuntu 22.04、ROS 2 Humble、C++17、colcon和libcurl开发依赖。下列命令基于仓库放在`~/ZKXWN`：

```bash
cd ~/ZKXWN/versions/v8
bash ./scripts/test.sh
bash ./scripts/build.sh
bash ./scripts/run.sh A 2
```

`cd`进入本版的程序目录；`bash`执行对应Shell脚本。`test.sh`是检查，`build.sh`是构建，`run.sh A 2`启动A席位第二阶段；第一个参数可改席位，第二个参数`1/2`代表阶段。裁判需要另行启动，公开ROS域及网关按现场要求配置，不能据启动成功认定获得真实AI资格。

切换版本前先停止旧节点，避免同一席位多个程序同时发动作。真实令牌只放运行环境，不提交仓库。

先读[8.0独立检验补充](独立检验补充.md)，其中的重复计伤、临时墙等待、挡枪误判及旧公告污染等问题仍保留在本历史源码中。不要把README中的性能目标当作已消除这些缺陷。

## 原交付说明（保留历史内容）

# 校内8.0

保存日期：2026-10-24。官方规则仍为 v1.1（`02_官方规则_v1.1_当前/`），8.0 是程序版本。

8.0 以 7.0 为底子重写了几处决策，修掉了 7.0 的一批漏洞。目标是**性能**：同样的地图、同样的席位、同样的对手，8.0 自己能拿更高的分，而且更稳。下面所有比较都是这种“同一环境各打一局”的比法，不是让 8.0 去专门针对 7.0。

全部场景双方非法动作都是 0。8.0 对 8.0 的对称检查分差严格为 0。完整 28 组见[性能验证报告.md](性能验证报告.md)。

**要说清楚的地方：**

- 四人局里，对手越强，差距越小。对手全是 7.0 时是 +0.73；对手全是 8.0 时只有 +0.31（区间含 0）。第二阶段资源总量固定、四家分；7.0 的伤害平均已经在 500 封顶附近；任务完成率又受开局抢速度限制。8.0 的提升主要来自把伤害稳在 500 以上：3×7.0 阵容里伤害满线率 94% 对 73%。资源和任务基本持平，任务数还低了 0.04。
- 让 8.0 和 7.0 坐进同一局直接比，两者几乎打平（+0.06，区间 [−0.75, +0.80]）。8.0 比 7.0 更能拿分，但不靠“针对 7.0”。
- 这些都是离线仿真。真实比赛的地图、对手和事件都不同，数字不能直接外推，详见下面“已验证与未验证”。

## 8.0 改了什么

1. **第一阶段：边探图边规划路线。** 7.0 先把看见的资源吃完再探图，所有资源平均到第 82.5 Tick 才被看全，角落常被漏掉。8.0 把“未知区域的观察点”和已知资源放进同一条最优路线（定向越野精确 DP），已知资源优先，探图只占用富余时间。规则公布了资源总数（16 个），露面完就不再绕路。300 张图里，“从没看见过”而漏掉的资源从 144 个降到 48 个。
2. **第二阶段开局：同样的观察点路线**，按可见敌人的距离给可能被抢的资源打折。只在“没有更要紧的事”时参与：能开火、血量低于 50、有天使/堡垒/辣椒事件时，都不出这个目标。
3. **第二阶段后期：主动找人打。** 7.0 资源采完以后 70% 以上的 Tick 在漫游，追猎半径只有 5 格。8.0 的追猎覆盖整个视野。看不见敌人时，去任务点、地图中心、四个象限巡逻；还会按自己出生点的镜像推测别人的复活点。
4. **识别不开火的对手。** 7.0 按“对齐就会开火”的最坏情况防御。碰到只打相邻目标的对手，会在原地连续防御几百 Tick（同一局面下 200 Tick 里 200 次 DEFEND，见 `scripts/defect_cases.sh`）。8.0 记录每个敌人对齐时有没有真的掉血，连续 3 次没开火就不再把它当威胁，战斗预估里也不让它开火。
5. **容错的事件计划解析。** 7.0 只要模型输出有一处不合规就整份作废：同时写了 events 和 hazards、多一条认不出的 kind、重复 id、用了规则原文名字（如 pepper）、漏写数值都算。8.0 逐条校验，坏条目只丢那一条；缺的数值用规则正文公布的标准值补。
6. **模型调用链路。** 7.0 的公告一变，就把正在路上的结果当过时丢掉；超时只有 2.5 秒，超时后还重试 3 次（网关可能已扣了配额）；事件话题只留最后 1 条。8.0 只丢“比已采用计划还旧”的结果；超时改为 15 秒，读超时不重试；整场公告去重累积后一起发给模型；请求频率随剩余配额自动放慢；事件话题按协议用深度 128。用真实节点代码 + 本地假网关实测：模型每次要 3 秒时，**7.0 节点 17 次成功调用、用上 0 份计划，8.0 节点 13 次调用、用上 13 份**（`evidence/node_sim/`）。
7. **测评工具重写。** 7.0 的仿真裁判没有任何随机事件，它报告里的“事件局优势”从来没被测过。8.0 的离线裁判按规则 PDF §5.2 的顺序实现 8 种事件、击杀奖励、死亡扣除和第一阶段动作限制，由一个“理想模型”把公告翻成结构化计划，分别交给 7.0、8.0 各自的解析器。

逐条的漏洞、影响和证据见 [7.0检查报告.md](7.0检查报告.md)。改动清单见 [更新日志.md](更新日志.md)。

```bash
cd ~/校内8.0

```

```bash

```

同一输入下 7.0 与 8.0 的实际输出对照（模型输出的毛病、原地防御死锁）。

```bash
./scripts/bench.sh --a 8 --b 7 --field 777 --maps 100 --seed 120000
```

8.0 与冻结的 7.0 各坐同一席位、面对同一批对手各打一局。`--field` 指定另外三个席位：`7` 为 7.0，`8` 为 8.0，`g` 为贪心，`r` 为冲锋，`c` 为只采集，`w` 为掉线。`--events standard|practice` 开随机事件，`--noise 1|2|3` 模拟模型输出的毛病，`--stage 1` 测第一阶段。7.0 的决策核心已冻结在 `baseline_v7/`（与校内7.0 逐字相同），不需要 7.0 文件夹。

```bash
./scripts/node_sim.sh 83000 2 100 standard
```

不装 ROS，把真正的 `node.cpp`、`llm.cpp`、`curl_transport.cpp` 跑一整场：感知 JSON、动作 JSON 都按协议格式收发，模型请求通过 libcurl 发往本地假网关。需要 C++17 编译器、libcurl、python3。前面加 `NODE=7` 跑 7.0 的节点做对照，需要 7.0 源码：默认找同级的 `../校内7.0`，不在同级时用 `V7_ROOT=7.0文件夹路径` 指定（例如 `V7_ROOT=~/Downloads/校内7.0`）；`MOCK_LATENCY_MS=3000` 模拟慢模型，`MOCK_FAIL_EVERY=3` 注入网关故障。

```bash
python3 tools/evaluate.py --arena build_arena/rmtc_arena --out evidence/rerun_01
```

重跑全部 28 组测评（先运行一次 bench.sh 生成 `build_arena/rmtc_arena`）。输出目录必须是新目录，不会覆盖原始证据。

## 启动 ROS 节点（Ubuntu 22.04 / ROS 2 Humble）

```bash
./scripts/build.sh
export ROS_DOMAIN_ID=27
export RMTC_AI_GATEWAY=http://裁判机IP:8000
export RMTC_TEAM_TOKEN=本场席位令牌
./scripts/run.sh A 2
```

依次编译 ROS 包，设置通信域、网关地址和本场令牌，以 A 席位启动第二阶段。需要 colcon 和 libcurl 开发包。裁判另外启动，正式域号和地址以主办方通知为准。换版本前先停掉旧节点，避免同一席位有两个程序发动作。

本版命名空间 `rmtc8`，ROS 包和可执行文件 `rmtc_bot8`，包版本 `8.0.0`，默认队名 `HERO-8.0`。现场档位文件仍只含 `decision_type`，支持 `balanced`（默认，追猎半径 10）、`collect`（追猎半径 5）、`fight`（更激进）。所有决策参数都写死在源码里，没有任何环境变量或隐藏参数通道：规则只允许现场改 `decision_type`。

## 已验证与未验证

**已验证（macOS，Apple clang；CMake 4.4 + CTest 与无 cmake 两条路径都通过）：**
- 六组测试 4076 项断言零失败：141 核心回归、11 模型线程、641 规则边界、3228 情景/性质、23 条 7.0 契约、32 条 8.0 新契约。
- 28 组离线测评，所有策略非法动作为 0。
- 真实节点代码（用 ROS 替身头文件编译）+ 真实 libcurl + 本地假网关跑整场：每 Tick 都发出动作，tick/session 回填错误 0，动作格式错误 0，无效动作 0，第 0 Tick 取得 AI 资格调用。
- 决策耗时（离线、10 线程并发测量）：无事件 p99 约 0.16 ms；有事件时时间展开 BFS 较重，p99 约 3.3 ms、最大约 60 ms。离 500 ms 的 Tick 很远，但比 7.0 报告写的“最大 0.4 ms”高，那个数字是在无事件条件下测的。

**未验证：**
- 没有在 Ubuntu + ROS 2 Humble 上构建和运行真实 ROS 节点，也没有跨机 DDS。ROS 替身只验证了代码逻辑和协议格式，不能代替现场检录。
- 没有连真实的统一 AI 网关和真实模型。真实模型对公告的理解好坏直接决定事件局表现；离线测评里的“理想模型”是上限。
- 没有在官方裁判测试端上打完整场，事件的最终口径（堡垒驻留、分裂复活保护等）以裁判为准。
- 离线对手（7.0、贪心、冲锋、只采集、掉线）只是代表性样本，正式比赛的对手是其他队伍的程序。

本包是完整源码和资料，不含编译产物、真实凭据或参赛二进制。官方三份 PDF 和 dist.zip 保留原始字节，`文件清单.json` 可用于完整性核对。
