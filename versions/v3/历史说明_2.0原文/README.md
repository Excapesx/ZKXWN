# 校内 2.0 —— 针对 1.0 的对抗版参赛程序

> 版本 v1.0 · 2026-10-23 · 适用规则 **v1.1**（赛事规则 / 通信协议 / 裁判测试端 v1.1）
> 目标：在同图、同规则、同席位轮换的条件下，**稳定赢过 校内1.0**。

---

## 一、一句话结论

**1.0 的问题不是写错了，而是"算错了价"。** 它把资源、伤害、死亡混在几套经验权重里比较，导致整场比赛几乎不主动接战（实测 600 场平均有效伤害 **8.7/500**，折合对抗分 **0.26/15**）。

2.0 只做了一件事：**把所有候选动作折算成同一个单位——真实比分增量**，于是每一 Tick 都自然选择"这一步值多少分"。结果是资源基本没少拿，对抗分从 0.26 拉到满分 15。

| 指标（300 张地图 × 2 次席位轮换 = 600 场） | 校内 1.0 | **校内 2.0** |
|---|---|---|
| 四人对局平均总分（满分 60） | 25.21 | **34.78** |
| 有效伤害 D（满分 500） | 8.7 | **604.1** |
| 资源价值 R2 | 49.1 | 47.1 |
| 完成任务数（满分 3） | 2.53 | 2.50 |
| 头对头胜率 | — | **75.0%**（450 胜 / 7 平 / 143 负） |
| 决策耗时 p99 | 93.3 µs | **23.7 µs** |

完整方法与数据见 [03_对抗验证报告](03_对抗验证报告.md)。

## 三、快速开始（Ubuntu 22.04 / ROS 2 Humble）

```bash
# 1) 编译
./scripts/build.sh

# 2) 启动（席位 A、第一阶段）
export ROS_DOMAIN_ID=27
export RMTC_TEAM_TOKEN='本场席位令牌'
export RMTC_AI_GATEWAY='http://<裁判机IP>:8000'
./scripts/run.sh A 1

# 3) 第二阶段（带 LLM）
export RMTC_AI_GATEWAY='http://127.0.0.1:8080'   # 练习端代理
./scripts/run.sh A 2
```

环境变量：

| 变量 | 含义 | 默认 |
|---|---|---|
| `RMTC_TEAM_TOKEN` | 本场席位令牌（**只从环境读，不写日志**） | 空（不调 LLM） |
| `RMTC_AI_GATEWAY` | 统一网关地址 | 空 |
| `RMTC_MODEL` / `RMTC_MAX_TOKENS` | 模型名与输出上限 | 网关默认 |
| `RMTC_MAX_TICKS` | 覆盖 Tick 上限 | 100 / 500 |
| `RMTC_DECISION_CONFIG` | `decision_config.json` 路径 | 内置 balanced |

现场只改 `decision_config.json` 的 `decision_type`，取值三选一：
`balanced`（默认）/ `collect`（保守采集）/ `fight`（强对抗）。

## 四、本地对抗基准（可选，用于自检）

基准会把 **1.0 的真实决策代码**（`Stage1Policy` / `Stage2Policy` / `DecisionEngine`）
和 2.0 编进同一个仿真裁判，跑同图同规则对局。

```bash
# Linux
LEGACY=../校内1.0/01_程序源码/ZKXWN ./scripts/bench.sh --stage 2 --matches 300 --robots 4

# 已在本机用 MSVC 19.51 验证（x64, /std:c++17 /O2）
```

参数：`--stage 1|2`、`--matches N`、`--robots 2|4`、`--seed N`。

> 注意：`tools/bench/` 是**内部评测工具**，不提交、不进入比赛镜像。
> 它链接 1.0 代码只为"对手就是本人"，不影响 2.0 的独立性。

## 五、相对 1.0 的五个结构性改动

| # | 1.0 的做法 | 2.0 的做法 | 效果 |
|---|---|---|---|
| 1 | 第一阶段用 `value × exp(-到达/50)` 打分，且最多展开 6 段 | 用**定向越野精确 DP**（≤13 个目标穷举最优，>13 贪心+插入），目标函数就是**实收总价值** | 阶段一 38.50 vs 37.93 |
| 2 | 伤害按 `(15/500)×伤害` 计价，再减 `0.06×受伤` | 伤害、击杀奖励、死亡扣 60 **同口径**折算；封顶前 0.03/点，封顶后只剩补刀价值 | 对抗分 0.26 → 15 |
| 3 | 受到攻击威胁时按"所有可见敌人都会开火"的上界惩罚 | 只在**真会被打死**时才防御，其余用走位脱离射线 | 死亡 1.27 vs 1.05，但输出差 70 倍 |
| 4 | 每个候选目标各跑一次 BFS（时间维展开时是 `cells×(T+1)`） | 每 Tick **一次 BFS 距离场**，所有目标查询 O(1) | p99 23.7 µs vs 93.3 µs |
| 5 | 感知遇到未知实体类型整帧抛异常；阶段与任务不匹配就完全不出手 | 未知类型跳过、缺任务照常决策、任何异常都退化为合法动作 | 不会因协议扩展整场 WAIT |

## 六、规则对齐（v1.1 硬性要求）

| 规则条款 | 落实方式 |
|---|---|
| 动作必须回填 `tick` / `session_id` | `action_json()` 从当前感知原样回填，节点层再校验一次 |
| QoS：感知/动作 `RELIABLE / VOLATILE / KEEP_LAST(1)` | `rclcpp::QoS(KeepLast(1)).reliable().durability_volatile()` |
| 事件公告 `RELIABLE / TRANSIENT_LOCAL / 128` | 独立订阅 `/referee/event_text`，深度 128 |
| 随机事件必须由 LLM 理解，禁止正则/关键词 | 只把公告原文交给模型，本地仅做**结构校验**与过期处理 |
| 第二阶段每场至少一次真实 AI 成功调用 | 开场即请求；未成功则每 20 Tick 重试，直到成功或硬阻塞（401/quota） |
| 不得读取其他席位/全图/隐藏配置 | 只用 `/team_X/perception`、`/referee/event_text`、`/referee/mission` |
| 现场只能改 `decision_type` | 只读 `decision_config.json` 的单一字段，枚举三选一 |

## 七、已知边界（必须知道）

1. **随机事件链路未在真实网关上跑过。** 代码路径完整（异步、超时、429、401、输出校验、降级），但没有真实令牌做过端到端验收；上场前必须按 04 文档做一次真机联调。
2. **基准裁判是自研的**，覆盖移动争格、攻击射线、防御减伤、死亡复活、资源、任务、D 的加减顺序；**不覆盖**爆炸/幻术/无双/辣椒等事件结算。所以数据只说明"无事件条件下的策略强弱"。
3. **1.0 的代码未改动**，适配层只做了"感知结构体转换 + 按真实席位构造"，不改变其任何决策逻辑。
4. 对局人数影响结论：4 人局优势最大（75%），1v1 因双方都接近"资源 30 + 任务 15"的天花板，优势收窄到 57.5%。正式赛是 4 人局。
