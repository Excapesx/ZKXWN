# 01 · 校内 1.0 弱点分析

> 分析对象：`01_程序源码/ZKXWN`，固定提交 `f2f6eae`（交接包声明）。
> 所有行号对应该提交的源码；引用格式 `文件:行号`，可逐条复核。
> 原则：只列**能指出代码位置、能说明后果、能被验证**的问题。不评价风格。

---

## 0. 先给结论

1.0 的工程质量不低：协议字段校验严格、动作合法性有守卫、有 55 张地图的回归、文档写得比代码还细。
它真正的短板只有一个 —— **决策的"价格体系"不对**：

> 同一个决策里，资源用"分值/距离"比较，伤害用"0.03/点"比较，死亡用"100 的固定罚"比较。
> 三套单位混在一起取最大值，结果就是**只要敌人可能反击，攻击永远算不过"再走一步去捡资源"**。

实测后果很直接：600 场四人局里，1.0 的平均有效伤害 **8.7 / 500**（对抗分 0.26 / 15），
而资源拿了 49.1（与 2.0 的 47.1 基本持平）。**它不是没资源，是完全没有对抗分。**

## 1. 弱点清单

### W1 · 第一阶段的打分函数与真实得分不一致

**代码证据**

```cpp
// rmtc_ws/src/rmtc_bot/src/policies/stage1_policy.cpp:48
beam.push_back({..., targets[i].resource.value * std::exp(-d / 50.0)});
// :64
tour.reward + targets[j].resource.value * std::exp(-arrival / 50.0)
```

**问题**
第一阶段得分是 `40 × R1 / 200`，**只跟"最终收了多少价值"有关，与什么时候收到无关**。
但巡游评分对到达时间做了指数折扣：第 40 Tick 才拿到的 10 分资源只算 `10×e^-0.8 ≈ 4.5`。
于是"顺路但晚到"的资源被系统性低估，路线会提前收束。

**量化**
300 张同图对比：1.0 平均收 `189.7/200`，2.0 收 `192.5/200`；1.0 有 40 张图输、2.0 只有 72 张图赢，其余 188 张打平。
差距不大 —— 因为 20×20 地图、16 个资源足够密，100 Tick 基本能吃满。**这条是"少赢半分"，不是决定性弱点。**

**2.0 的应对**
目标函数改成真实得分：`max Σvalue, s.t. 路径长度 ≤ 剩余 Tick`（定向越野），DP 精确求解，见 W2。

### W2 · 第一阶段搜索被"6 段 + 16 个目标"卡死

**代码证据**

```cpp
// stage1_policy.cpp:36   最多记 16 个目标
if(targets.size()>16)targets.resize(16);
// stage1_policy.cpp:56   束搜索最多 5 段（depth 从 1 到 5）
for(int depth=1;depth<6;++depth) {
```

**问题**
即便不谈折扣，束搜索只展开 5 段行程、束宽 64、目标上限 16。
16 个资源里要选 8~10 个时，最优解**根本不在搜索空间里**。

**2.0 的应对**
`solve_tour()`：目标数 ≤13 时用 `dp[mask][last]` 的精确 DP（2^13×13 ≈ 10 万状态），
>13 时退化为"价值/绕路成本"贪心 + 插入。
`tests/core_tests.cpp::test_tour_optimal` 用 40 组随机算例与全排列暴力对拍，**结果完全一致**。

### W3 · 伤害定价太低、受伤惩罚太高 —— 这是最致命的一条

**代码证据**

```cpp
// decision/src/engine.cpp:162  damage_reward()
double reward = (15.0 / 500.0) * std::min(damage, std::max(0.0, 500 - s.score.effective_damage));
// → 一次普通攻击 20 点 = 0.6 分（utility 单位）

// decision/src/engine.cpp:424  每次候选都要减"本 Tick 会受到的全部伤害"
double utility = reward - w.current_damage * std::min(s.self.hp, now+after_event) - w.future_damage * later;
// 默认权重 current_damage = 0.06 → 被反击 20 点 = -1.2
```

**问题**
对射一次：收益 `+0.6`，被反击成本 `-1.2`，**净收益恒为负**。
只要对手"可能"朝自己开火（而 W4 会把这个"可能"放大成"一定"），引擎就永远不会选择攻击。
于是整场比赛退化成"躲避 + 采集"，对抗分恒等于 0。

**量化（600 场四人局）**

| | 1.0 | 2.0 |
|---|---|---|
| 有效伤害 D | **8.7** | **604.1** |
| 对抗分 | 0.26 / 15 | 15 / 15 |
| 击杀 | 0.16 | 4.25 |

1.0 打了 600 场，平均每场只造成 8.7 点伤害——**不到一次普通攻击的一半**。

**2.0 的应对**
`attack_value()` 把一次攻击折算成真实比分：
`0.03 × min(实际伤害 + 击杀 60, 500 − D)`，并在 `D ≥ 500` 后把系数压到 0.3；
只有"残血且打不死对方"才额外扣风险。于是"能打就打"变成数学上的正收益。

### W4 · 威胁模型是"全员开火"的上界，导致过度防御

**代码证据**

```cpp
// decision/src/engine.cpp:126
// Conservative estimate: every visible eligible enemy chooses to fire.
if (!screened) result += defending ? 10 : 20;
```

**问题**
把"所有看得见、能打到的敌人都会朝我开火"当作确定性事实，而不是上界。
四人局里同时被 2~3 台车瞄准是常态，`incoming` 直接变成 40~60，
配合 W3 的 0.06 系数，任何前压动作的 utility 都是负的。

**2.0 的应对**
只统计"真的站在射线上、且中间没有遮挡"的敌人；被瞄准时先算**能不能走出射线**（走位候选），
走不掉且必死才 `defend`。基准里 2.0 的死亡数 1.27 与 1.0 的 1.05 接近，但输出差 70 倍 ——
说明它不是靠"不怕死"，是靠"算清了什么时候不会死"。

### W5 · 死亡惩罚是硬编码常数，与 D 的实际价值脱钩

**代码证据**

```cpp
// decision/src/engine.cpp:195-205
struct Weights { double attack=1; double current_damage=0.06; double future_damage=0.04; double death=100; };
if (mode == Mode::Aggressive) return {1.8, 0.03, 0.015, 60};
if (mode == Mode::Survival)   return {0.45, 0.10, 0.09, 140};
// :439
if (fatal_now) utility -= w.death;
```

**问题**
v1.1 里死亡的真实代价是 **−60 有效伤害**，而有效伤害只在 500 以内值分。
所以：
- `D = 0` 时死亡的真实代价 ≈ **0 分**（只损失 3 Tick 和位置）；
- `D = 480` 时死亡 ≈ **1.8 分**。

1.0 用固定 100（或 60/140）的罚分去近似，既没有"早死便宜、晚死昂贵"的梯度，
也和 0.03/点 的伤害收益不在一个量纲上。

**2.0 的应对**
`combat_points(D) = 0.03 × min(D, 500)`，死亡直接按 `combat_points(D−60) − combat_points(D)` 结算，
不引入任何额外常数。**开局 D=0 时敢换血，赛末 D 接近 500 时自然收手** —— 这个梯度是免费的。

### W6 · 击杀奖励 60 没有进入候选评分

**代码证据**
1.0 自己的交接文档已经写明（`docs/RULES_V1.1_DELTA.md` "建议继续补的部分 1"）：

> 现在 `damage_reward` 只看本次名义伤害（20/10），没有把"击杀额外 60"单独算进候选收益。

**后果**
500 点对抗分里，击杀奖励占 `60/160 ≈ 37%`（一次击杀 = 100 伤害 + 60 奖励）。
不算这一项，等于把"补刀"和"普通消耗"视为等价，**错过了效率最高的一类动作**。

**2.0 的应对**
`attack_value()` 里 `delta = dmg + (kill ? 60 : 0)`，且"补刀"额外加 1.2 的节奏价值
（对手 3 Tick 复活 + 回出生点，在资源争夺里等于让出 2~3 个资源）。
基准中 2.0 场均击杀 4.25，1.0 为 0.16。

### W7 · LLM 只要成功过一次，后续解析失败就永久不再重试

**代码证据**

```cpp
// rmtc_ws/src/rmtc_bot/src/runtime.cpp:64
const bool retry_without_success = !llm_success_seen_ && !hard_blocked &&
    (tick-last_llm_attempt_tick_ >= 25);
// :66
if(!requested_ || changed || retry_without_success) { llm_.submit(...); }
```

**问题**
`llm_success_seen_` 一旦为真，就只剩 `changed`（公告文本变化）能触发新请求。
如果某次公告的模型输出被判为"结构不合法"，`parse_llm_response` 返回空，
计划不更新、**也不会重试**，后面的危险区预报就一直是旧的，直到下一条公告。

**风险等级**
未在本地基准触发（基准关闭事件）。属于"上线后才会暴露"的一类问题。

**2.0 的应对**
把"HTTP 成功"和"解析成功"分开记：解析失败但 HTTP 成功 → 保留本次调用资格（配额已花），
**但计划不更新，并在 20 Tick 后重新请求一次**（最多 2 次），避免一次坏输出导致全盲。

### W8 · 感知过于严格：一个未知字段就丢整帧

**代码证据**

```cpp
// rmtc_ws/src/rmtc_bot/src/perception.cpp:97
else throw std::runtime_error("Unsupported entity type; incomplete observation");
// :39
if (text.size() != 89) throw std::runtime_error("Relative position must have 9 rows of 9 characters");
```

**问题**
`parse_perception` 抛异常 → `runtime.handle()` 直接返回空 → **该 Tick 不发布任何动作**（裁判按 WAIT 结算）。
协议明确写了"实体按 vision_radius 筛选"，未来版本增加一个实体类型是完全可能的；
一个类型名就能让整场变成木头人。

**2.0 的应对**
`parse_perception` 对未知 `type` **跳过该实体**而不是丢帧；相对位置串先剔除 `\r` 再校验；
关键字段（tick/session/map/self）缺失才失败。

### W9 · 阶段与任务不匹配时，直接不出手

**代码证据**

```cpp
// rmtc_ws/src/rmtc_bot/src/runtime.cpp:35
if(config_.stage==1 && !p.missions.empty()) { reason_="stage1_but_missions_present"; return {}; }
// :36
if(config_.stage==2 && p.missions.empty()) { reason_="stage2_but_no_missions"; return {}; }
```

**问题**
这是"防呆"设计，出发点是对的（防止阶段配错）。但代价是：**只要裁判端多给/少给一个字段，整场 0 分**。
第二阶段的任务内容"不固定"，`missions` 数组的形态由主办方决定；把"必须有任务"当作硬前提，
风险收益比不划算。

**2.0 的应对**
没有 `missions` 时按 `mission_text` + 常识目标继续打（资源 + 对抗），
只是拿不到任务分，而不是整场不动。

### W10 · 规划器性能：每个候选目标各跑一次 BFS

**代码证据**

```cpp
// decision/src/engine.cpp:318  add_goal() 内部
route = planner_.plan({s.self.position, target, s.width, s.height, blocked});
// rmtc_ws/src/rmtc_bot/src/planner.cpp:73  时间维展开时按 cells×(horizon+1) 分配
std::vector<bool> seen(cells*(timed?static_cast<std::size_t>(horizon+1):1),false);
```

**问题**
第二阶段 `add_goal` 会对每个资源、任务点、每个探索前沿各调一次 `plan()`。
无事件时靠 BFS 树缓存勉强顶住；**一旦 LLM 给出危险区（`regions_` 非空），`timed` 为真，缓存失效**，
每次调用都要开一个 `cells×(T+1)` 的数组做时空 BFS。24×24、T=500 时是 28 万节点/次 × 上百次候选。

**实测**
600 场四人局：1.0 决策 p50 **29.8 µs**、p99 **93.3 µs**；2.0 为 **11.7 / 23.7 µs**。
（本机 MSVC Release。绝对值不代表赛场机器，但相对差距稳定。）
尚未突破 500 ms 窗口，但**余量比 2.0 小 4 倍**，且这是"没有事件"的前提下的数字。

**2.0 的应对**
每 Tick 只做**一次** `bfs()`，得到 `dist[]` 与 `first[]`；之后任何目标查询都是 O(1)。
危险区在 BFS 前合并进阻挡掩码，不进入时间维。

## 3. 我没有做的事（边界声明）

为了避免"为了赢而违规"，以下手段**明确没有采用**：

- ❌ 不读全图 / 不读其他席位感知 / 不读观赛接口；
- ❌ 不解析结构化事件参数，事件只走 LLM + 公开公告；
- ❌ 不使用 1.0 的任何代码或权重（`tools/bench/legacy_adapter.cpp` 只在本地评测里链接它，
  且位于 `tools/`，不进入 `ros2_ws` 编译产物）；
- ❌ 不针对 1.0 的"具体下一步"做预测（那需要读它的内部状态，属于越界）。

2.0 赢的方式是**在规则内把分算对**，而不是找 1.0 的漏洞。
