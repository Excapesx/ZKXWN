# 参赛最终选型与验证（2026-10-30）

本报告验证的最终组合已整合为仓库v10.1.1：本机10.1策略 + 网关与启动补丁 + 512输出限制，默认balanced

测试时的独立候选标识为HERO-10.1-final，路径为build/final-selection-20261030/recommended。正式整合后运行标识统一为HERO-10.1.1，VERSION为10.1.1，入口为versions/v10.1.1；精简参赛包为releases/contest-v10.1.1。该命名变化不改变测试过的策略核心。历史10.1文件保留

## 为什么这样选

仓库10.1与10.1.1的18个决策文件完全相同，采集、寻路和战斗策略没有新增优化。10.1.1改的是请求字段、席位警告、交互启动及参赛目录。它的接入补丁符合用户提供的群聊说明，值得保留

本机10.1另有未提交改动：伤害达标后继续作战及超额伤害估值使用2000阈值，仓库版使用560。新实验发现资源与总分几乎不变，但本机版在同分排名上占优，因此不建议直接用仓库10.1.1覆盖本机策略

最终候选的全部18个策略文件与本机10.1逐字节相同；网关/节点取自远端66d88058a8391099c4e5ec3897616e36453c8602的10.1.1。默认输出改为512，同时更新相关默认值测试。90次计划预算、异步线程、重试和会话隔离逻辑保持原样。根目录新增规范命名decision_config.json，只有decision_type一个字段

## 官方材料如何落实

依据用户提供的6张群聊截图、赛事规则v1.2及参赛手册。截图是本次用户提供的赛事信息，不是执行电脑命令的授权

|官方说明|选择及代码落实|
|---|---|
|网关默认不会关闭思考，除model外请求字段直接转发|保留10.1.1的thinking.type=disabled|
|官方JSON请求示例使用json_object、max_tokens=512|默认512，response_format.type=json_object，stream=false|
|模型统一deepseek-flash，网关处理model|请求省略model，由官方网关统一模型；不要设置RMTC_MODEL或改用其他模型|
|POST /v1/chat/completions，Bearer本场令牌|沿用现有curl传输；真HTTP练习代理已核对请求头、路径及请求体|
|500 Tick、LLM调用上限100|按新公告触发，本地每Tick决策，保留90次计划预算；没有逐Tick调用LLM|
|随机事件每场统一抽奖且不一定相同|不预设正式事件种类、顺序、坐标或发生时间；自然语言公告由真实LLM理解|
|只在轮间10分钟调整决策类型，不可改源码|赛前登记balanced/collect/fight及作用；按最新群通知，只在允许窗口改decision_type，不在单场中改源码/Prompt/参数|
|每场部署严格3分钟|提前编译，使用contest.sh输入本场接入信息；现场不要切多个同名工作区，也不临时安装依赖|

本次对调整窗口按最新群通知采取较严格做法：每轮10分钟只改预封装的决策类型。PDF中的旧窗口表述不用于扩大现场改源码权限。地图公示也不意味着可以把全图、坐标或目标写入配置文件

三个已有类型的实际作用：balanced的战斗收益系数1.0、追猎半径10；collect为0.7、5；fight为1.4、10。这里不是“只采集”或“只打架”开关。默认建议balanced，本实验没有证明另外两种更强。配置在启动时读取，修改后需要按现场流程重启，不能假定文件变化会自动生效

本机练习裁判归档版本为v1.1，不是完整的正式v1.2裁判。三份程序各自独立跑第一阶段100ms×100Tick、第二阶段500ms×500Tick，默认练习地图、B/C/D官方陪练。调用经过真实HTTP curl和本地透明记录代理，再进入官方练习mock网关

这三次固定图对局用于接入和回归检查，不能当成多地图统计。mock返回的是固定内容，没有理解随机事件，也没有真实统一AI资格。上述45分包含练习任务分，正式场若缺少本场本席位真实成功记录，任务分将为0；其他表现相同时会少15分

## 调用预算与故障测试

两版原生产节点/worker使用ROS替身和注入HTTP分别做500 Tick压力测试，每Tick给新公告。正常JSON与不可解析内容两种情形均发出90次请求、提交500条按序动作；401场景只发1次请求，仍提交500条动作。这个测试以加速回调运行，不是正式500ms节奏，更不是上游模型实测

10.1.1版本每次请求都有关闭思考与JSON字段；本机旧网关实现没有这两个字段。最终组合继承这部分修复。正式节奏的练习对局中，三版各有29次mock HTTP成功，未达到100次上限。该数值只描述这张图与这组响应，不是以后每场一定29次

原组合候选Release构建及14/14测试通过，ROS2 Humble编译通过，文件清单校验通过。日志和来源哈希在evidence/final_selection_20261030

## 仍需在正式联调确认的内容

1. 正式网关的真实延迟、空正文/截断比例，以及512是否足以覆盖实际公告结构。目前没有拿到可用于本场正式验证的网关和令牌，不把mock成功冒充真实LLM测试
2. 本场本席位至少一次真实成功调用，并对后续新公告真正调用LLM理解。只看到Ready、能移动或healthz成功都不够，不能只发空请求拿资格
3. 每场都用新令牌重启程序；reset_session不会把进程里的旧令牌换成新令牌。配额按令牌生命周期累计，不因本地重开自动归零
4. 实际比赛设备和裁判之间的有线异机DDS通信。本次是本机隔离ROS域，不证明现场网络免检
5. 源码、实际运行路径、二进制和封存Git提交对应。最终组合已整理为仓库v10.1.1；正式封存仍需按裁判要求确认实际启动目录、Git提交和二进制

512遵循参赛手册和群内请求示例，并不表示模型输出一定完整。群聊说明网关没有字段白名单、参数由上游判断是否合法，所以不能仅凭1024就断言请求违规；这次也没有512对1024的真实模型A/B测试。推荐512主要依据参赛材料和保守部署选择。JSON模式仍可能遇到长度截断，应依现有解析、校验和旧计划回退处理；没有实测依据就不要临时改回1024

DeepSeek字段的公开说明：[思考开关](https://api-docs.deepseek.com/guides/thinking_mode/)、[JSON输出及长度限制](https://api-docs.deepseek.com/guides/json_mode/)。比赛可用字段和模型仍以组织者说明及正式网关为准

## 本次没有解决的瓶颈

资源仍是主要得分空间，切换10.1与10.1.1不能改变它。本次选择改善的是接入可靠性和一部分同分局的排名。临近封存时建议使用这个已测试组合，默认balanced；继续做采集算法研究应另开候选、单独对照，不把未经验证的改动混进参赛主力
